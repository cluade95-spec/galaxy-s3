# Phase 2 preparation: authenticating the GT-I8200 kernel source and stock firmware

**Date:** 2026-11-05 · **Scope:** decide whether the Koloses kernel (`44afe4c`) is a trustworthy base, and set up a safe, verifiable way to get the official kernel source and stock firmware for the GT-I8200.
**Rules followed:** no kernel modifications, no compiling, no flashing, nothing written to any phone, no firmware downloaded. I fetched web *listing pages* (metadata) and read files from public Git repositories. I read two kernel images already sitting in community repositories (decompressing and inspecting them as data, never running them).

> **Update (same day, after the approved computer-only build):** see [phase-2-kernel-build.md](phase-2-kernel-build.md). Built with the original toolchain and Samsung's production options, the Koloses source reproduces the genuine I8200XXUAOC1 kernel's code byte for byte (all 5,144,576 code bytes; 41,847 of 41,847 symbols identical in name, size and address; 26 bytes differ in the whole image after normalising the build-folder path). That upgrades the verdict in section 1 from "plausible" to "compiled code verified equivalent to a genuine Samsung GT-I8200 release kernel". It is still not compared with Samsung's own download.

## 1. Verdict

**The Koloses kernel is a plausible, internally consistent copy of a Samsung GT-I8200 kernel source, but it is not authenticated. I do not recommend treating it as "official" yet. It is acceptable as a provisional working reference. Kernel modifications should wait until one of the checks in section 7 passes.**

Why not simply "yes":

1. **Samsung's own servers are unreachable from here.** `opensource.samsung.com` and Samsung's firmware servers still return HTTP 403 through this environment's network policy (rechecked today). So there is no official copy to compare against.
2. **Nobody has ever stated which Samsung release it is.** Its repository calls it "I8200XXUAOC1" (March 2015). Its own build files say it was compiled on 13 January 2016, which fits the newest GT-I8200 firmware, I8200XXUAPB1 (17 February 2016), better. Section 6.3 sets out the three candidates.
3. **I can't rule out that the repository owner changed something.** I found no sign of it (section 6.2), but the evidence below can't detect small logic edits.

Why not "no": every test I could run without compiling agrees with it (section 6.2). Most importantly, **98.4% of the function and variable names in a genuine Samsung GT-I8200 kernel from March 2015 appear in the Koloses source, and I reviewed every one of the remaining 406 and all are generated by macros or build tables, not real code missing from the tree**. Where the Koloses tree differs from an older Samsung GT-I8200N tree in compiled code, the genuine kernel follows the Koloses version.

## 3. Official kernel source: how to obtain and authenticate it

### 3.1 State of access (re-tested today)

| Host | Purpose | Result |
|---|---|---|
| `opensource.samsung.com` | Samsung Open Source Release Center (the official place for the kernel archive) | **403 (blocked by network policy)** |
| `fota-cloud-dn.ospserver.net`, `neofussvr.sslcs.cdngc.net`, `cloud-neofussvr.samsungmobile.com` | Samsung firmware servers | 403 |
| `samfw.com`, `www.sammobile.com`, `xdaforums.com` | Third-party mirrors / forum | 403 |
| `samfrew.com`, `archive.org`, `github.com` | Third-party mirror (listing pages only), archive, Git | reachable |

### 3.2 What I could not establish

- **The exact name of Samsung's package.** Searches found none. A 2017 forum post (known to me only through a search snippet) says searching `gt-i8200` on the Release Center returns the **GT-I8200N** source, which raises the possibility that Samsung published no separate GT-I8200 package. **CLAIMED, secondhand.**
- **Whether the Release Center shows a checksum.** Not checkable from here. Do not assume it does.
- A community mirror of Samsung packages (`Samsung-OSS-Kernels` on GitHub, 72 repositories) labels its packages like `SM-T210_EUR_KK`, `GT-I9082_SEA_JB`, i.e. `<MODEL>_<REGION>_<ANDROID>`. It has nothing for the GT-I8200. This hints at the naming pattern to look for (probably `GT-I8200_EUR_JB` or similar), nothing more. **CLAIMED.**

### 3.3 Procedure

Do this on your own computer, or here once `opensource.samsung.com` is allowed (Environment settings → Network access → Allowed domains; steps at https://code.claude.com/docs/en/cloud-environments#network-access).

1. Open https://opensource.samsung.com and search for `GT-I8200` (also try `I8200`). Record every result's **package name, model list, upload date and file size** exactly as shown. Take a screenshot.
2. **Do not substitute silently.** If results list only `GT-I8200N` (or `I8200N`), stop and tell me. Then the question becomes whether a GT-I8200N package is acceptable for a GT-I8200. Section 4.2 shows Samsung sometimes builds both from one changelist, so the answer may be yes for some releases, but that has to be decided release by release and with your approval.
3. Pick the package whose upload date is closest to, and not before, 17 Feb 2016 (the I8200XXUAPB1 release). If there is also an older package, download both and note which is which.
4. Download over HTTPS directly from the Release Center. Accept the licence page. Save the file exactly as named. Compute and record **SHA-256, MD5 and byte size** (`sha256sum file`).
5. Authenticity checks to record (none alone is proof):
   - The file came from `opensource.samsung.com` over HTTPS (screenshot and file name).
   - Inside the archive, the README states the model (`HOW TO BUILD KERNEL 3.4.5 FOR GT-I8200…` or `…I8200N…`), as the older Samsung I8200N package does.
   - The tree contains `pxa986_golden_rev02_defconfig` and `pxa986_goldennf_rev02_defconfig`.
   - Compare with the Koloses tree using the method in 6.2 and appendix B. Acceptance criteria are in section 7.
6. Add the archive's name, size and hashes to this file's section 9. Do not commit the archive itself (large); keep it outside the repository or in a release attachment.

## 4. Stock firmware: what to fetch and how to do it safely

### 4.1 The exact package needed

The target is **PDA/AP version `I8200XXUAPB1`** (build date 17 Feb 2016, changelist 2893589, Android 4.2.2) **for model `GT-I8200` exactly**. It is the latest GT-I8200 build and the only GT-I8200 build after March 2015. It is the latest for four regions (CSC codes). Third-party metadata:

| CSC region | CSC version string | Modem (phone) version | Listed size | Source |
|---|---|---|---|---|
| SER (Russia) | `I8200QXEAPG1` (samfrew also lists `I8200OXEAPG1`) | `I8200XXUAPC1` | ~710 MB (`QXE`), ~704 MB (`OXE`) | bot + samfrew |
| SEE (Serbia) | `I8200OXXAPC1` | `I8200XXUAPC1` | ~706 MB | bot + samfrew |
| BGL (Bulgaria) | `I8200OXXAPA1` | `I8200XXUAPA1` | ~706 MB | bot + samfrew |
| VVT (Bulgaria) | `I8200VVTAPB1` | `I8200XXUAPA1` | ~699 MB | bot + samfrew |

All four share PDA `I8200XXUAPB1` and changelist 2893589. The bot is `JeyKul/fwcheck2` (snapshot `03c0b40755534e68e6da9a0f2d2be28a0ae66fc9`, which records Samsung's update-server answers); the sizes and dates come from samfrew.com listing pages fetched today. **Both are CLAIMED.** The full table of every GT-I8200, GT-I8200N, GT-I8200Q and GT-I8200L version, date and changelist I found is in `docs/data/firmware-changelists.tsv`.

For extracting the kernel, boot image, ramdisk and partition layout, the region should not matter, because the PDA part is the same string in all four. **That is expected but not verified.** If your own phone's CSC is different, you will still extract the same kind of data. The modem version differs between regions (`UAPA1` vs `UAPC1`), which does not matter for the kernel.

Consequences:

- **GT-I8200Q shares the codename `goldenvess3g` and often the same changelist as GT-I8200**, so a codename check alone cannot tell them apart. The model string must be checked inside the package.
- A GT-I8200N package at a **shared** changelist is the same source as the GT-I8200 build. At **OC1 and PB1 it is not**: N has no build at 2893589.

### 4.3 Where the firmware may come from (ranked)

| Rank | Source | What it can prove | Use? |
|---|---|---|---|
| 1 | **Samsung's own update servers** (the "FUS" service), reached with an open-source client run on your computer (for example SamFirm, samloader or Frija). I could not reach these servers from here, so I describe general behaviour from memory, not verified from this environment: the server reports the file name, byte size and a CRC for each package, and the client decrypts it | The file came from Samsung. Record size and CRC. | **Preferred** |
| 2 | A third-party mirror (samfrew, sammobile, samfw, firmwarehome, rompz and similar) | Nothing by itself. A good-looking file is not proof. Only the `.tar.md5` MD5, which detects accidental corruption, not tampering. | **Only if** its byte size and CRC match what Samsung's server reports for the same version (querying the server for those two numbers does not need the 700 MB download) |
| 3 | Any mirror with no way to cross-check | nothing | **Do not use** |

I am not downloading from a mirror and I am not asking you to. Samsung does not, to my knowledge, publish checksums for old firmware on a public page, so route 1 is the only way to establish where a file came from.

### 4.4 Identity gates (every one must pass before any file is opened)

1. File name contains `I8200XXUAPB1` and **does not** contain `I8200N`, `I8200Q`, `I8200L`, `I8190`, `I8190N` or any other model.
2. The source page says model **`GT-I8200`** exactly. Mirror pages list many models together. Check the row, not the page title.
3. Size is in the expected range (about 700 MB) and matches Samsung's reported size (route 1).
4. After unpacking (read-only, offline): `ro.product.model=GT-I8200`, `ro.product.device=goldenvess3g`, `ro.product.name=goldenvess3gxx`, and a build fingerprint ending in `I8200XXUAPB1:user/release-keys` (compare `ro.build.fingerprint` in the system image's `build.prop`).
5. The kernel banner inside the boot image reads `Linux version 3.4.5-2893589 (se.infra@…)` and the embedded path contains `GOLDENVESS3G_EUR-XX_USER`. These are my predictions from the pattern in section 2. If either differs, stop.
6. Nothing is flashed. The unpacked files are analysed on a computer, never sent to a phone.

### 4.5 Read-only identity checks you can do on the phone

These only display information; they change nothing.

- **Settings → About device**: Model number (must read `GT-I8200`), Baseband version, Build number (format `JDQ39.I8200XXUA…`).
- Dialling `*#1234#` shows PDA / CSC / Phone versions on Samsung phones of this era (display only). **Do not use other secret codes**, because some change settings or CSC.

Please send me those three values and the CSC. It will pick the correct package row in 4.1.

## Appendix B: Symbol-coverage method (T2), no compiling

1. Decompress the zImage payload (a gzip stream after the decompressor stub).
2. Extract the built-in symbol table with `kallsyms-finder` (PyPI package `vmlinux-to-elf`, run in a virtualenv).
3. Index every identifier in the source tree's `.c .h .S` files and test each non-generated symbol name against that index. Drop names the compiler or macros create (`ftrace_*`, `__kstrtab_*`, `CSWTCH*`, `fops_*`, suffixes such as `.isra.0`).
4. Report coverage and review the residue by hand.
